# LongBench 数据集选型分析报告

## 目的

本文档对 LongBench 全部 21 个数据集进行系统梳理，从 **ai-context-manager 插件上下文管理能力** 的测试角度出发，挑选出最具代表性的评测数据集，为后续基准测试方案设计提供依据。

---

## 一、ai-context-manager 核心能力维度

在进行数据集选型前，先明确需要评测的能力维度：

| 能力维度 | 对应配置参数 | 测试目标 |
|---------|------------|---------|
| **消息数量截断** | `max_messages` + `summarize_strategy: truncate/sliding_window` | 截断后模型能否仍回答当前问题 |
| **Token 数量截断** | `max_tokens` + `token_estimate_ratio` | Token 超限后关键信息是否保留 |
| **上下文压缩（Compaction）** | `summarize_strategy: compaction` + `compaction_interval` / `token_threshold` | 压缩摘要是否保留了足够信息来回答查询 |
| **重叠窗口** | `overlap_size` | 压缩边界处信息是否连续 |
| **系统提示词保护** | `preserve_system_message` | 系统指令在截断/压缩后是否完整 |
| **对话轮次完整性** | `preserve_turn_pairs` | 截断后 user-assistant 配对是否完整 |
| **长对话持续理解** | 全局 | 极长对话中多轮管理后的信息留存率 |
| **中文上下文管理** | 同上 | 中文对话场景的专项验证 |

## 三、适合测试上下文管理能力的数据集筛选

### 筛选标准

1. **上下文长度**：输入须足够长（≥ 4K tokens），能触发截断/压缩
2. **信息分布**：答案所需信息分布在上下文多处，截断可能影响正确性
3. **对话/轮次结构**：优先含多轮对话结构，直接模拟插件真实使用场景
4. **可量化评估**：有客观度量标准，便于比较管理前后的性能差异
5. **中文覆盖**：需含中文数据集，验证中文对话场景下的管理效果

---

### ✅ 第一梯队：强烈推荐（最直接测试上下文管理能力）

#### 1. QMSum（多轮会议对话摘要）

- **平均长度**：~10,600 tokens
- **推荐理由**：
  - 输入本身是**多轮对话格式**（speaker: utterance），与 ai-context-manager 处理的 `messages` 数组结构高度吻合
  - 任务为**查询驱动型摘要**，需要从长对话中定位相关轮次，完美模拟"截断/压缩后能否回答关于早期对话内容的问题"
  - 可直接测试 `compaction` 策略：压缩后摘要是否保留了足以生成正确答案的信息
  - 可测试 `preserve_turn_pairs`：截断时 user-assistant 对完整性对答案质量的影响
- **测试能力**：上下文压缩质量、轮次完整性、信息保留率

#### 2. VCSUM（中文多轮会议摘要）

- **平均长度**：~15,400 tokens
- **推荐理由**：
  - 中文版 QMSum，对话更长，Token 数更多，更容易触发多次上下文管理
  - 验证插件在**中文多轮对话**场景下的上下文管理效果
  - 长度超过多数模型上下文窗口，必须依赖 `max_tokens`/`token_threshold` 触发管理
- **测试能力**：中文上下文管理、极长对话压缩效果

#### 3. PassageRetrieval-en（英文段落检索）

- **平均长度**：~9,300 tokens
- **推荐理由**：
  - **针刺大海捞针式**（Needle-in-a-Haystack）测试：30 个段落中有一个是目标，必须精确检索
  - 直接量化"截断/压缩后目标信息是否幸存"，灵敏度极高
  - 若插件截断了含有目标段落的部分，准确率骤降为 0，提供清晰的失败信号
  - 可系统测试不同 `max_messages`/`overlap_size` 组合对信息保留的影响
- **测试能力**：关键信息保留、截断策略精确度

#### 4. PassageRetrieval-zh（中文段落检索）

- **平均长度**：~6,700 tokens
- **推荐理由**：
  - PassageRetrieval-en 的中文版，提供中文场景下的相同测试
  - 验证中文 Token 估算（`token_estimate_ratio`）是否准确
- **测试能力**：中文关键信息保留、中文 Token 估算精度

---

### ✅ 第二梯队：推荐（良好的上下文管理评测价值）

#### 5. NarrativeQA（超长叙事文本 QA）

- **平均长度**：~18,000 tokens（最长，含整本书/剧本）
- **推荐理由**：
  - 最长上下文数据集，**极端压力测试**场景
  - 故事理解需要全局信息，截断破坏叙事完整性会直接影响回答
  - 最能体现 `sliding_window` vs `compaction` 策略在长文本上的性能差异
- **测试能力**：极端长度压力测试、策略对比（截断 vs 压缩）

#### 6. MuSiQue（复杂四跳推理）

- **平均长度**：~11,100 tokens
- **推荐理由**：
  - 4 个文档的四跳推理链，推理步骤最多
  - 上下文管理若移除了推理链中任一步骤所需的文档，推理将断裂
  - 测试 `preserve_turn_pairs` + `pinned_message_roles` 能否保护推理过程
- **测试能力**：多跳推理链完整性、消息固定策略效果

#### 7. HotpotQA（二跳推理）

- **平均长度**：~9,200 tokens
- **推荐理由**：
  - 跨文档二跳推理，需同时访问两篇文档
  - 比 MuSiQue 简单，适合作为基线对比
  - 压缩/截断后推理能力损失可量化
- **测试能力**：跨上下文推理保持能力

#### 8. GovReport（长文档摘要）

- **平均长度**：~8,700 tokens
- **推荐理由**：
  - 单文档完整摘要任务，文档结构清晰
  - 压缩后生成的摘要质量（ROUGE 分数）能直接反映信息保留程度
  - 适合测试 `compaction` 压缩摘要的质量基线
- **测试能力**：压缩摘要质量、信息蒸馏效果

---

### 🔶 第三梯队：可选（有一定测试价值，但针对性较弱）

#### 9. 2WikiMultihopQA（Wikipedia 多跳推理）

- **平均长度**：~4,900 tokens
- **推荐理由**：多跳推理但长度适中，适合测试较小上下文窗口配置
- **局限性**：长度偏短，较少触发上下文管理

#### 10. DuReader（中文多文档 QA）

- **平均长度**：~15,000 tokens
- **推荐理由**：中文多文档，测试中文多文档场景下的上下文管理
- **局限性**：任务形式为 QA 而非对话，与插件使用场景稍有差距

#### 11. LSHT（中文超长文档分类）

- **平均长度**：~22,600 tokens（全部数据集中最长）
- **推荐理由**：极端长度的中文少样本分类，测试 `max_tokens` 的上限处理
- **局限性**：分类任务，不涉及对话结构，主要测试极端截断场景

#### 12. MultiFieldQA-zh（中文多领域 QA）

- **平均长度**：~6,000 tokens
- **推荐理由**：中文多领域文档，验证中文 Token 估算和截断逻辑
- **局限性**：长度一般，场景覆盖不如 QMSum/VCSUM

#### 13. MultiFieldQA-en（英文多领域 QA）

- **平均长度**：~4,500 tokens
- **推荐理由**：多领域文档，测试非对话类英文文档的上下文管理
- **局限性**：长度偏短，覆盖场景有限

---

### ❌ 不推荐（相关性较低）

| 数据集 | 不推荐原因 |
|-------|----------|
| **TREC** | 问题分类任务，输入为短问题序列，不模拟对话管理 |
| **TriviaQA** | 少样本格式，答案通常在单段落内，不测试长程信息保留 |
| **SAMSum** | 平均长度仅 2,800 tokens，无法触发上下文管理 |
| **MultiNews** | 平均长度仅 2,100 tokens，上下文太短 |
| **PassageCount** | 计数任务，测试精确信息保留；但计数结果受截断影响的规律过于简单 |
| **LCC** | 代码补全，与对话上下文管理场景差异较大 |
| **RepoBench-P** | 跨文件代码补全，属于代码工程场景，与对话管理无直接关联 |
| **Qasper** | 长度偏短（3,600 tokens），且为论文证据型 QA，场景代表性有限 |

## 五、推荐数据集与插件功能的映射关系

| 插件功能 | 推荐评测数据集 |
|---------|-------------|
| `summarize_strategy: sliding_window` | NarrativeQA、PassageRetrieval-en/zh、HotpotQA |
| `summarize_strategy: compaction` + `compaction_interval` | QMSum、VCSUM、MuSiQue、GovReport |
| `token_threshold` 触发压缩 | NarrativeQA（~18K）、LSHT（~22.6K）、VCSUM（~15.4K）、DuReader（~15K） |
| `max_messages` 截断 | QMSum（多轮对话）、VCSUM（多轮中文对话） |
| `preserve_turn_pairs` | QMSum、VCSUM（天然的 speaker-utterance 配对） |
| `overlap_size` 边界连续性 | MuSiQue（推理链跨边界）、QMSum（跨轮摘要连续性） |
| `pinned_message_roles` | MuSiQue（固定推理支撑信息）、HotpotQA |
| 中文 Token 估算精度 | VCSUM、PassageRetrieval-zh、DuReader、MultiFieldQA-zh、LSHT |
| `preserve_system_message` | 所有数据集（通过系统提示注入任务指令验证） |

## 六、结论

**最优先实施**的 4 个数据集为：

1. **QMSum** —— 最直接模拟多轮对话管理场景，英文主力测试集
2. **VCSUM** —— 中文长对话场景，中文测试主力
3. **PassageRetrieval-en** —— 信息保留的精确度测试，截断效果最直观
4. **PassageRetrieval-zh** —— 中文信息保留测试

这 4 个数据集能够覆盖 ai-context-manager 最核心的测试需求（多轮对话管理、信息保留、中英文双语），且均提供客观评价指标，便于量化比较不同配置参数对上下文管理效果的影响。
